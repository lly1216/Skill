## 是什么与为什么

下位机（lower-level controller）是直接驱动电机、读取编码器与 IMU 的实时控制器，通常是 MCU 或带实时核的工控板；上位机（upper-level controller）是跑 ROS 2 与业务程序的 Linux 主机。本文件讲两者怎么连、协议怎么定、厂家 SDK 怎么读，以及网络不通时怎么分层定位。

### 三层职责与一条命令的时序

- 上位机：规划、决策、状态显示、日志，周期 10–100 Hz，非硬实时，允许卡顿——但卡顿的后果必须由下位机兜住。
- 下位机：电流环/位置环、PWM 输出、传感器采样，周期 1 ms 或更快，硬实时，绝不能被通信阻塞。
- 中间层：物理链路 + 协议。协议必须回答三件事——命令能否被确认、丢包怎么办、失联时谁负责停。

一条命令的完整时序：上位机组帧 → 下发 → 下位机校验（SOF/长度/CRC/seq）→ 执行 → 回带同一 `request_id` 的 ACK → 周期性状态帧 → 上位机超时未收 ACK 则重试 → 连续丢失 N 个心跳后下位机进入安全态、上位机标记 `OFFLINE`。**安全停止必须由下位机独立完成**，不能依赖上位机再发一条"停止"。

### 通信方式怎么选

| 方式 | 典型场景 | 优点 | 代价与限制 | 选它的判据 |
|---|---|---|---|---|
| 以太网（Ethernet） | 上位机与主控、相机、激光雷达互联 | 带宽高、通用、易调试 | 需配 IP 与网段，交换机引入延迟 | 有 IP 可配、要传图像或点云 |
| TCP | 指令下发与确认、文件与配置读写 | 可靠有序、有重传与流控 | 重传带来延迟抖动、队头阻塞 | 命令不能丢、能容忍几十毫秒抖动 |
| UDP | 高频状态广播、遥测、时间同步 | 延迟低、无连接、开销小 | 会丢包乱序，需自己做序号与容错 | 高频只读数据、丢一帧不致命 |
| CAN / CAN FD | 关节电机、电池管理、底盘驱动器 | 差分抗干扰、多主广播、硬件仲裁与 CRC | 带宽低（经典 CAN 载荷 8 B，CAN FD 到 64 B）、拓扑受限 | 多节点短帧、强干扰、要确定性 |
| RS485 | 低成本传感器、老式驱动器、云台 | 差分、可多点、线可长 | 半双工，常需主机轮询，无仲裁 | 节点少、速率低、成本敏感 |
| UART | 板内模块间、调试串口、GPS/IMU 模块 | 极简单，几乎无协议栈 | 点对点、TTL 电平、无错误恢复 | 两个器件直连、距离很短 |
| USB | 相机、调试口、固件升级、手柄 | 带宽高、即插即用、能供电 | 无实时保证、线短、可能掉枚举 | 大带宽或需要热插拔 |
| EtherCAT | 多轴伺服同步、分布式 IO | 周期可到毫秒以下、时钟同步精度高 | 需专用主站与从站芯片，门槛高 | 多轴强同步，普通轮询不够用 |
| MQTT | 云侧跨网遥测与指令、手机 App 通道 | 发布订阅、穿透 NAT、支持 QoS | 走 TCP 经 broker 中转，延迟不确定 | 跨网络、多订阅者、非硬实时 |

取舍原则：**控制环内用确定性总线（CAN / EtherCAT / 以太网直连），控制环外用 MQTT**。不要把急停或关节闭环放在 MQTT 上，那是在拿网络抖动赌人身安全。

## 最小可运行示例

约定：命令示例默认 Ubuntu Bash；Python 示例依赖 3.10+，MQTT 示例依赖 paho-mqtt 2.x。所有 `<...>` 占位值必须来自设备手册或 SDK 配置文件，**不得猜**。

### 1. 只读确认链路与端口（Ubuntu Bash）

```bash
ip -br addr                 # 本机各网卡地址：有没有同网段 IPv4
ip -br link                 # 网卡 UP/DOWN 与 MAC
ip route                    # 默认路由与同网段直连路由
ping -c 3 -W 1 <机器人IP>    # 丢包率应为 0
ss -lntup                   # 本机监听；没装 ss 时用 netstat -lntup
nc -vz -w 2 <机器人IP> <端口> # -w 2 是 2 秒连接超时，不能省
```

网卡 `UP`、与设备同网段、ping 通、端口可连，四条都过才继续。端口号以 SDK 文档或设备手册为准（**待核实**）。

### 2. Python 最小 UDP 收发（标准库）

```python
import socket

DST = ("<机器人IP>", 0)          # 待核实：端口以 SDK 文档/配置文件为准
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.settimeout(0.2)                # 200 ms，约等于 2 个 100 Hz 控制周期
s.sendto(b"\xAA\x55", DST)       # 占位帧；真实帧格式见协议文档
try:
    data, addr = s.recvfrom(2048)
    print("RX", addr, data.hex())
except socket.timeout:
    print("TIMEOUT：按下方判断树从 IP/路由/防火墙/设备端依次排除")
```

### 3. MQTT 最小验证（paho-mqtt 2.x）

```python
import time
import paho.mqtt.client as mqtt

def on_message(client, userdata, msg):
    print(msg.topic, msg.payload[:64])

c = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2)
c.on_message = on_message
c.connect("<broker地址>", 1883, keepalive=30)   # 1883 是 MQTT 默认端口，TLS 为 8883
c.subscribe("<主题前缀>/#")                     # 主题名以设备/broker 配置为准，不得臆造
c.loop_start(); time.sleep(10); c.disconnect()
```

`CallbackAPIVersion` 是 paho-mqtt 2.x 的强制参数，照抄 1.x 教程会直接报错——这是"旧教程跑不通"的第一大原因。

## 工程实现要点

### 帧格式与校验

| 字段 | 宽度 | 说明 |
|---|---|---|
| 帧头 SOF | 2 B | 固定 `0xAA55`，用于在字节流里快速同步 |
| 版本 | 1 B | 收到不认识的版本直接丢帧，不要猜 |
| 载荷长度 | 2 B | 只算载荷，不含帧头与 CRC |
| 序列号 seq | 2 B | 每帧递增、允许回绕，用于丢包与重放检测 |
| 消息 ID | 2 B | 命令字，需配套命令表（含方向、频率、单位） |
| 载荷 | N B | 定长结构体或 CBOR；浮点端序统一约定 |
| CRC16 | 2 B | CRC16-CCITT，覆盖"版本到载荷" |

解析必须用环形缓冲（ring buffer）累积字节：先找 SOF，再按长度取整帧，校验通过才交给上层。**不要假设一次 `recv()` 就是一帧**——TCP 是字节流，UDP 也会丢包乱序。CAN 帧有硬件 CRC，但应用层仍要用 seq + 时间戳防重放。

### 心跳、超时、重连（默认值与依据）

| 项 | 默认值 | 依据 |
|---|---|---|
| 上位机→下位机心跳 | 1 Hz | 远低于控制周期，几乎不占带宽 |
| 下位机→上位机状态帧 | 10–50 Hz | 够状态显示与日志，不挤占控制总线 |
| 失联判定 | 连续丢 3 个心跳（约 3 s） | 容忍 1–2 次抖动，3 次仍无应答基本可判死 |
| 单命令 ACK 超时 | 板内总线 100 ms / 网络 500 ms | 留出排队时间，又远小于人的反应时间 |
| 重试 | 最多 2 次（共 3 次），退避 50/150 ms | 沿用项目约定：不得无限重试 |
| 网络连接/读取超时 | 连接 3 s / 读取 5 s | 沿用项目统一默认值 |
| 重连退避 | 1s→2s→4s→8s，上限 30 s，±20% 抖动 | 断网时避免所有设备同时重连打满 |

重连后的动作顺序写死：重新握手 → 确认使能状态（默认保持失能）→ 重新同步状态。**绝不自动恢复上一条运动命令**。

### MCU 侧基础

- PWM：定时器通道输出。电机驱动常用 20 kHz 以上（避开可听噪声、减小电流纹波），舵机类 50 Hz、脉宽 1–2 ms 对应行程两端；具体频率、脉宽映射与死区以驱动器手册为准（**待核实**）。
- 编码器：定时器编码器模式做正交解码，读 32 位计数差分得速度；必须处理 32 位回绕与低速量化误差，速度做一阶低通（如 α=0.2）。
- IMU：SPI/I2C 读取，采样 200–1000 Hz；上电先做零偏标定，把安装方向与坐标轴对齐写成文档（与 ROS 2 侧坐标系约定要能对上）。
- 实时性：中断服务程序只做"置标志 + 拷数据"；浮点运算、`printf`、动态内存分配一律移出中断；串口用 DMA + 环形缓冲。
- Watchdog（看门狗）：用独立看门狗，喂狗点放在主控制循环的固定位置。任务卡死即复位，**复位后默认进入电机失能/阻尼的安全态**，而不是自动续跑上一个动作。
- 裸机与 RTOS 取舍：裸机前后台 + 超循环，控制环少于 3 条、无复杂通信时最稳，无栈溢出与优先级坑；风险是"一个大 `while` 塞所有事 + 一堆 delay"，某路通信一阻塞整机停摆。RTOS（FreeRTOS / Zephyr 等）支持多任务、优先级、队列与信号量，适合"控制 + 多路通信 + 日志"并存，代价是栈溢出、优先级反转、临界区保护。判据：**通信任务会不会把控制周期拖长**？会拖长就是硬实时被破坏，必须改 DMA/中断架构或引入 RTOS。

### 拿到 SDK / GitHub 项目 / 协议文档的标准分析流程

只读准备：源码复制到独立目录，`git log --oneline | head`，通读 README / CHANGELOG / 文档目录；不在原始目录改配置，改前 `cp config.yaml config.yaml.bak`。

1. **入口程序**：找 `main`、`examples/`、`demo/`、`scripts/`，同时看构建文件（`CMakeLists.txt` / `Makefile` / `pyproject.toml` / `setup.py`）确定可执行目标与依赖。
2. **通信模块**：全局搜 `socket`、`serial`、`can`、`paho`、`mqtt`、`send`、`recv`，确定"谁在发、谁在收、收包跑在哪个线程"。
3. **控制 API**：看公共头文件 / 导出符号 / 包的 `__all__` / 文档 api 章节，列出可调用的高层接口。**没亲眼读到的接口名一律写 `待核实`**。
4. **初始化流程**：`init()` / `connect()` 之前做了什么——起网卡、设 IP、`can up`、申请权限、加载标定文件。
5. **IP / 网卡配置**：找 `*.yaml` / `*.json` / `*.ini` / `.env` / `config/`，用 `ip addr` 核对本机与设备是否同网段。
6. **连接**：只连接、只握手，不使能电机；把日志级别调到 DEBUG。
7. **读状态**：只调只读接口（电量、温度、关节角、IMU），记录**单位、符号、坐标系、频率**——这是后续所有控制的基准。
8. **发运动命令**：过安全门禁 G0→G1（仿真 → 低速低力矩 → 单关节 → 短时长 → 手边有人能断电）。回滚方式：预先确认失能与阻尼接口可用，异常时用物理急停断电。
9. **安全停止**：先把停止接口验证通过，再验证运动接口。分清软急停、失能、阻尼三种停法的差别，并确认拔网线/断心跳时设备自己会不会停。

### 分层网络排查判断树

纪律：以下命令默认 Ubuntu Bash（Windows 侧已注明），每步只跑 1–3 条；跑之前先写下"预期看到什么"，结果不符再决定下一步，**不要一次甩几十条命令**。先是归类现象（不跑命令）：SDK 报的是 connect 失败还是连上没数据？换一台电脑能通吗？之前通过吗？

**第 1 步 本机地址**：`ip -br addr; ip -br link`。网卡 `UP` 且有与设备同网段的 IPv4 → 第 2 步；`DOWN` → 网卡/驱动/线缆问题（`sudo ip link set <if> up`，仍 DOWN 看 `dmesg | tail`）；有 IP 但网段不对 → **IP 配置问题**；只有 `10.0.2.x` / `172.17.x` / `192.168.56.x` 一类地址 → 大概率**虚拟机 NAT / 仅主机网络**，不是设备网段。

**第 2 步 链路与邻居**：`ip -s link show <if> | tail -5`、`ip neigh`（旧系统用 `arp -n`）。`RX packets` 增长且 `errors/dropped` 为 0 → 二层通；邻居 `REACHABLE` → IP 层可达，`FAILED` / `INCOMPLETE` → 二层不通或对端不回 ARP；TX 增长而 RX 恒为 0 → 对端没发或线缆问题，**物理层/设备端**。

**第 3 步 路由**：`ip route get <设备IP>`。出口网卡正是你要的那张 → 路由正常；走了默认网关或别的网卡 → **路由问题**，先用 `ip route add` 临时验证，确认后再持久化。

**第 4 步 连通性**：`ping -c 3 -W 1 <设备IP>`。通 → 第 5 步，问题在端口/应用/SDK；不通但 ARP 正常 → 对端可能禁 ICMP，继续做端口测试；`Destination Host Unreachable` 且 `ip neigh` 为 FAILED → 退回第 2 步。

**第 5 步 端口与连接状态**：`ss -lntup`、`nc -vz -w 2 <设备IP> <端口>`。本机该服务没监听 → **SDK/应用没启动**；外连停在 `SYN-SENT` → 被防火墙拦或对端没开端口；`Connection refused` → 对端可达但端口没人听，**设备端服务问题**；一直 timeout → 多在防火墙或对端完全不响应。

**第 6 步 防火墙**：`sudo ufw status verbose`、`sudo iptables -S | head -20`。有 `DROP` 命中目标端口 → **防火墙问题**；只放行必要来源 IP 与端口，不要整体关防火墙。

**第 7 步 抓包定责（最关键的一步）**：`sudo tcpdump -i <if> -nn -c 20 host <设备IP> and port <端口>`。有本机请求、无任何回包 → **设备端或其侧防火墙**；连请求包都没有 → **SDK/应用层没发出去**（连接没建立、读了错的配置、端口写错）；只有 ARP 来回、没有 IP 包 → 网段/路由问题；有回包但程序收不到 → 本机防火墙、绑定地址（`0.0.0.0` 与具体 IP 的差别）或收包线程没跑。**`-i` 选错网卡会得出"没有包"的错误结论**，多网卡机器先用 `ip route get` 确认出口网卡。

**第 8 步 虚拟机 / 容器边界**：VMware / VirtualBox 的 NAT 模式看不到设备所在物理网段，需改桥接（Bridged）并选对宿主机网卡，仅主机模式同样不通；WSL2 默认网卡与物理网段隔离，需网络镜像模式或端口转发（开关随版本变化，**待核实**当前版本的对应设置）；Docker 默认桥接网络到不了设备，Linux 下需 `--network host` 或显式路由。宿主机侧核对地址与网卡（Windows PowerShell）：`Get-NetIPAddress -AddressFamily IPv4`、`Get-NetAdapter`。宿主机能通、虚拟机不通 → **虚拟机网络模式问题**，不是设备问题。

**归属判断矩阵**

| 现象 | 归属 | 下一步 |
|---|---|---|
| 网卡 DOWN、无 carrier | 网卡/线缆 | 换线换口，看 `dmesg` |
| 双方网段不同或一方无 IPv4 | IP 配置 | 改地址或加 secondary IP |
| `ip route get` 走错网卡 | 路由 | 加明细路由并持久化 |
| 地址是 `10.0.2.x`/`172.17.x`，宿主机能通 | 虚拟机/容器 | 改桥接或 host 网络 |
| 外连 SYN-SENT/timeout，本机监听正常 | 防火墙/对端 | 查 ufw/iptables 与对端端口 |
| `ss` 里没有监听进程 | SDK/应用 | 看进程与启动日志 |
| 有请求无回包 | 设备端 | 抓对端日志或接串口看打印 |
| 能 ping 通但控制无反应 | SDK/设备端 | 查帧格式、使能状态、错误码 |

每步结论记到档案目录的 `triage/YYYY-MM-DD-主题.md`（档案目录解析见 `SKILL.md` 第 10 节）。

### 学习写法 vs 生产写法（以"下发一条运动命令"为例）

1. **初学者为什么这样写**：`while True: sock.sendto(cmd, addr); time.sleep(0.01)`——立刻能看到机器人动，反馈快，能建立直觉。
2. **企业怎么写**：`ControlService` 抽象层 + adapter（Mock / MQTT / SDK / ROS 2）；命令统一含 `device_id`、`command`、`parameters`、`request_id`、`timestamp`；ACK 超时 500 ms、指数退避重试最多 2 次；`request_id` 配 Redis 或唯一索引做幂等；状态机明确 `ONLINE / OFFLINE / TIMEOUT / COMMAND_FAILED`，设备离线时**不假装控制成功**；下发前过安全门禁。
3. **差别与原因**：循环直发回答不了"这条命令成没成功、重复发会不会执行两次、设备掉线时发生了什么、谁负责停"。生产要求可确认、可幂等、可回滚、可观测，代价是多一层抽象和状态机——这是能进公司代码库的最低门槛。

## 常见坑与验收标准

### 常见坑

1. 把一次 `recv()` 当一帧；TCP 是字节流，必须用环形缓冲 + SOF 同步。
2. 只在上位机做失联保护。网线一拔上位机也停了，**下位机必须能自己停**。
3. 心跳周期比控制周期还快，挤占总线导致控制抖动。
4. 重连后自动恢复上一条运动命令——断线时人可能正站在机器人旁边，必须停在失能态等人工确认。
5. 校验用异或或累加和，检错能力太弱；至少 CRC16-CCITT。
6. 没确认单位与坐标系：角度是度还是弧度、关节角是相对还是绝对，写错等于乱动。
7. 把 CAN / EtherCAT 的周期抖动当成"代码慢"；改代码前先打时间戳量真实周期。
8. 直接改厂家 SDK 源码，升级即丢失；优先用适配层包一层。
9. 依赖 `netstat` 而系统没装——Ubuntu 新版默认不带，`ss` 是等价替代。

## 学习路径

前置：C 语言指针与结构体、Linux 常用命令、TCP/UDP 基本概念、会用 `git clone` 读陌生代码。顺序建议：① 串口（UART）收发 + 自定义帧，字节可见，最适合建立"协议"直觉；② UDP/TCP 上位机脚本，同时用 tcpdump/Wireshark 对照，把"代码里的字节"与"线上的包"对上；③ CAN / CAN FD，先用 `candump` / `cansend` 看原始帧，再理解仲裁与位定时；④ MCU 侧 PWM 驱动一个电机 + 编码器读回速度跑通闭环，这一步才真正建立"控制周期"概念；⑤ 按上面的 9 步流程接入一个真实 SDK，全程留下只读验证与安全停止的证据；⑥ 最后再碰 EtherCAT 多轴同步与实时性调优。

里程碑证据：每步留下"命令 + 原始输出 + 一句结论"，写进档案目录的 `progress.md`；答不上来的知识点状态降级为"在学"。
