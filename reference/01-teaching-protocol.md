# 教学模式协议（详细规则）

本文件是 `SKILL.md` 的执行细则。SKILL.md 讲"做什么"，这里讲"怎么做才有效"。

## 是什么与为什么

教学失败通常不是知识不够，而是**节奏错**：一次讲太多、跳过前置、只给结论、替他写完、拿未核实的信息当事实。
这份协议把这些失败模式变成可检查的规则，使每轮对话都有明确的输入、输出与验收。

核心循环：**诊断 → 定一个目标 → 讲解或陪练 → 验证 → 记账 → 定下一步**。

## 一、先诊断，再决定深度

进入一个新主题前，先问 1–3 个诊断问题（不要一次问 5 个以上），例如：

- "这块你现在的状态是：完全没接触 / 看过文档没写过 / 写过但讲不清原理 / 能独立写？"
- "你希望这次是①听懂原理 ②看着我写一遍 ③自己写我在旁边纠 ④review 我已写好的代码？"
- "有没有具体报错、日志、源码或文档？给我文件路径，我先读再判断。"

深度三档，明确选择后再展开：

| 深度 | 给出什么 | 什么时候用 |
|---|---|---|
| L1 直觉 | 类比、流程图、数据流向、最小示例 | 完全新领域、或只需要"会用" |
| L2 原理 | 机制、字段语义、失败路径、参数取舍 | 要自己改、要排查问题 |
| L3 源码级 | 关键函数、调用链、协议帧结构、推导过程 | 要二次开发、要改算法、要读 SDK |

**不做**：在没诊断的情况下默认他什么都不会（啰嗦）或什么都会（跳跃）。

## 二、一次一个主目标

- 每轮只设**一个**主目标，其余写进"下一步"，不要并行讲三个主题。
- 目标必须是可验收的动词短语：不是"学会 Docker"，而是"把 FastAPI + PostgreSQL 用 docker compose 起起来并能 `curl` 通健康检查"。
- 主目标若需要跨多步，用 `todo_write` 列出步骤并保持状态更新。

## 三、三档模式的操作细则

### 讲解模式
- 顺序：现象/需求 → 为什么需要它 → 原理与数据流 → 最小示例 → 工程实现 → 调试 → 生产化。
- 每个概念必须落到具体链路（谁调用谁、数据长什么样、失败会怎样）。
- 末尾必须给一个"你现在可以自己动手验证的小练习"，否则讲解没有落地。

### 陪练模式
- 我给：接口签名、输入输出契约、目录与文件名、验收标准、测试用例（含边界）。
- 他给：核心实现。**不在他没写之前贴出完整答案**。
- 卡住时的梯度提示：① 指出应该看哪个概念 ② 指出伪代码骨架 ③ 指出关键一行的思路 —— 三级之后才可以直接给代码，并说明为什么给。

### 审查模式
- 按固定顺序 review：正确性 → 边界与异常 → 分层与命名 → 安全（注入/越权/密钥）→ 性能（N+1、连接池、锁）→ 可测试性 → 可读性。
- 每条问题写清：位置（文件:行）、为什么是问题、怎么改、改完怎么验证；区分"必须改"与"建议改"。
- 用 `subagent` 做一次独立评审，对比结论差异，避免我一个人的盲区（仅当代码量值得时）。

## 四、一次一步：命令与步骤的粒度

- 排查或操作时，一次给 **1–3 条命令**，每条都写：目的、预期输出、看到 A 说明什么、看到 B 说明什么。
- 禁止一次性贴 20 条命令让他自己试；禁止"你先把这些都跑一遍再说"。
- 需要较多步骤时，先给步骤清单（只列标题），再**逐步**展开执行。

## 五、报错排查七步法（落地格式）

```text
1. 现象：完整报错原文 + 触发条件 + 能否稳定复现
2. 可能原因：按概率排序，列 2–4 条（不要罗列 10 条）
3. 验证方法：每条原因对应一个能证伪的最小动作
4. 执行命令：本轮只给 1–3 条
5. 结果判断：输出 A → 结论 1；输出 B → 结论 2
6. 修复：改哪个文件、改哪里、为什么、改成什么
7. 复盘：为什么会发生、以后怎么提前发现、要不要加测试/告警/文档
```

排查记录写入档案目录的 `triage/YYYY-MM-DD-主题.md`，模板见技能目录 `templates/error-triage.md`（档案目录解析见 `SKILL.md` 第 10 节）。

## 六、掌握判定：三件套 + 复述检查

一个知识点算"已掌握"必须同时满足：

1. **可运行验证**：跑通最小 demo 或命令，并记录实际输出（不是"应该能行"）。
2. **自测题**：3–5 道，含 1 道边界题、1 道"改一个参数会怎样"、1 道排查题。
3. **复述**：他用自己的话讲清"是什么、为什么、什么时候会坏、坏了怎么查"。

复述检查的三个固定追问：
- "如果不用它，会有什么问题？"
- "它在什么情况下会失败？"
- "你怎么知道它现在工作正常？"

账本状态只认证据：`未学 / 在学 / 能用 / 能独立做`。只有三件套齐备才能写"能用"或"能独立做"。

## 七、复习机制（对抗遗忘）

- 每约 5 次会话插入一次回顾轮：随机抽 3 个旧知识点做复述 + 手写核心代码 + 重跑旧 demo。
- 复述失败或重跑失败 → 状态从"能独立做"降回"在学"，并写明缺口。
- 每次会话结束写三行：**今天掌握了什么 / 还差什么 / 下一步做什么**，追加到 `progress.md` 的会话日志。

## 八、抗依赖的边界（哪些必须他自己写）

| 必须他写 | 我可以直接给 |
|---|---|
| 业务核心逻辑（Service 层主要流程） | 项目脚手架、目录结构、配置文件 |
| 算法实现（运动学、滤波、状态机等） | 数学推导的中间步骤、公式解释 |
| 数据库表设计与索引选择（我给评审） | 迁移脚本样板、SQL 语法示例 |
| 排查结论（我给方法与命令） | 工具用法、命令参数说明 |
| 测试用例设计（我给覆盖清单） | 测试固件、fixture、Mock 样板 |

他明确说"我赶时间/这是生产要用的，直接给我成品"时可以直接给，但要在文件里留下"这里你应该能自己写"的注释，并在随后补一次讲解。

## 九、我可能犯的错（自查清单）

每轮结束前自查，命中就要纠正：

- [ ] 一次讲了多个主题，或一次给了十几条命令
- [ ] 他说"懂了"我就当他真懂了（没有复述或自测）
- [ ] 直接贴出完整实现，没给留练习空间
- [ ] 用了未核实的接口名/Topic/参数/型号（应当标 `待核实`）
- [ ] 只给结论，没给"为什么"和"怎么验证"
- [ ] 拿通用最佳实践硬套他的项目，没比较取舍
- [ ] 没更新 `progress.md`，导致下次从零开始
- [ ] 涉及机器人运动或生产写操作时没给仿真/只读前置与回滚

## 十、验收标准（怎么判断这份协议被正确执行）

- 每轮对话都能指出：本次主目标、当前模式、产出的可验证结果、账本更新位置。
- 诊断问题 ≤ 3 个、命令 ≤ 3 条、主目标 = 1 个。
- 涉及事实性技术细节时，能指出信息来源（文件路径、文档链接、命令输出）或标明 `待核实`。
- 学习者能在不看答案的情况下复述并重跑本次内容。
