# 安全与密码学（含密码 / 账本类 APP）

## 是什么与为什么

安全不是"加个 HTTPS、给密码做个哈希"的收尾工作，而是一条从**资产**倒推出来的设计链：先想清楚
"防谁、防什么"，再选密码学原语，最后才写代码。密码 / 账本类 APP 是"安全即第一需求"的
产品形态，它的正确做法同样适用于设备权限、订单与支付这类高风险路径。密码学解决三件事：机密性、
完整性、认证；安全工程解决第四件事：**即使这三条都成立，业务逻辑也不能被绕过**——真实事故极少
出在算法上，多出在越权、日志泄露、明文备份、弱口令与密钥管理。

### 威胁建模（先想清楚"防谁"）

用四个问题做一张四栏表，答案要写下来而不是留在脑子里：**资产**（口令库条目、主密码、主密钥、
备份文件、会话 Token、审计日志）；**对手**（手上有数据库文件的离线窃贼、被入侵的服务器运维、
同网段中间人、拿到手机的人、恶意的第三方依赖）；**攻击面**（登录、同步、导入导出、剪贴板、
系统云备份、崩溃日志与截图、SDK 依赖链）；**信任边界**（数据在哪些组件间流转、每段是否已加密）。
**零知识（zero-knowledge）的判定标准**：服务端被完全攻陷、数据库与备份全部泄露后，攻击者仍
无法解密条目。达到这条才算把信任边界画对；但条目数量、更新时间、设备列表这类元数据仍会泄露，
必须显式承认（它决定了"是否允许明文元数据"的取舍）。

## 最小可运行示例

两条链路严格分离，salt 与派生输出都不得复用：**验证链** 主密码 → Argon2id(salt_auth) →
`auth_hash`，只上传服务端做登录校验；**加密链** 主密码 → Argon2id(salt_enc) → `master_key` →
HKDF 派生逐条目密钥，永不上传。

```python
# 依赖: pip install "cryptography>=43"（Argon2id 在 cryptography 中需 OpenSSL>=3.2，否则用 argon2-cffi）
import os
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.kdf.argon2 import Argon2id
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

P = dict(time_cost=3, memory_cost=65536, parallelism=4, length=32)   # 64MiB, t=3, p=4

def master(pwd: bytes, salt_enc: bytes) -> bytes:      # 加密链：Argon2id 后再 HKDF 域分离
    seed = Argon2id(salt=salt_enc, **P).derive(pwd)    # 参数随密文存储，便于将来升级
    return HKDF(algorithm=hashes.SHA256(), length=32, salt=None,
                info=b"vault/master/v1").derive(seed)

def item_key(mk: bytes, uuid: str) -> bytes:           # 每条记录一把密钥 → nonce 重复风险趋零
    return HKDF(algorithm=hashes.SHA256(), length=32, salt=None,
                info=f"item/{uuid}".encode()).derive(mk)

def seal(mk: bytes, uuid: str, pt: bytes, aad: bytes) -> bytes:       # ver|params|salt|nonce|ct+tag
    nonce = os.urandom(12)                             # 唯一性来自 CSPRNG，不靠时间/计数器拼接
    return nonce + AESGCM(item_key(mk, uuid)).encrypt(nonce, pt, aad)

def open_(mk: bytes, uuid: str, blob: bytes, aad: bytes) -> bytes:    # 失败即抛异常，绝不降级
    return AESGCM(item_key(mk, uuid)).decrypt(blob[:12], blob[12:], aad)

if __name__ == "__main__":
    mk, aad = master(b"correct horse battery staple", os.urandom(16)), b"v1|item-0001"
    print(open_(mk, "item-0001", seal(mk, "item-0001", b"6222****", aad), aad).decode())
```

数据格式固定为 `version || kdf_params || salt || nonce || ciphertext||tag`：**没有版本号的数据
格式无法演进**，轮换与迁移的成本会直接变成"重新设计"。

## 工程实现要点

### 密码哈希与口令派生（KDF）

分开两个用途：服务端"验证口令"用慢哈希；客户端"派生加密密钥"必须用内存硬化 KDF。
**bcrypt 不适合做密钥派生**（无内存硬化、输出固定）。

| 算法 | 推荐参数 | 内存量级 | 出处类别 |
|---|---|---|---|
| Argon2id | m=64 MiB, t=3, p=4；资源受限下限 m=19 MiB, t=2, p=1 | 19–64 MiB | 官方文档（OWASP 密码存储备忘）+ 标准（RFC 9106） |
| scrypt / bcrypt | scrypt N=2^17, r=8, p=1（受限 N=2^14, r=8, p=5）；bcrypt cost=12 起，口令先 SHA-256 再 base64 以绕开 72 字节截断 | scrypt 128 MiB；bcrypt 极小 | 标准（RFC 7914）/ 经验值 + 官方文档 |

标定方法：在**最弱目标设备**上把单次耗时调到 **200–500 ms**；salt 每条记录、每条链路独立，≥16 字节；
口令最小长度 ≥12（推荐 16）、拒绝常见口令字典、允许口令短语；服务端用固定时间比较
（`hmac.compare_digest`）避免时序侧信道。`待核实`：各语言 bcrypt 绑定对 72 字节截断的具体处理，需读该库文档。

### 对称加密与 AEAD 要点

- 首选 **AES-256-GCM**；不要自创 AES-CBC + 独立 MAC 的组合，也不要为兼容性降级到它。
- **nonce 96 bit（12 字节）**，CSPRNG 生成，**每条记录、每次写入都全新**。
  同一密钥下密钥+nonce 重复是 GCM 唯一会灾难性失效的条件。
- NIST 对 96 bit 随机 nonce 的调用上限约 **2^32 次/密钥**（标准，SP 800-38D）。
  本地库难触及，但**同步服务端聚合写入要设阈值**，接近上限即轮换密钥（或按条目派生密钥规避）。
- **认证标签 128 bit**，不接受随意截断；**AAD 必须绑定不可变元数据**（格式版本、条目 UUID、
  设备 ID、字段类型），使"把 A 条目密文搬到 B 条目"这类重排攻击直接认证失败。
- 解密失败必须整条拒绝并计入审计；禁止"失败就用空值 / 旧值继续"。
- 需要独立完整性校验时用 **HMAC-SHA-256**（密钥 ≥32 字节）；密钥派生统一走 **HKDF-SHA256**
  （RFC 5869），用不同 `info` 做域分离，如 `vault/master/v1`、`item/<uuid>`、`backup/v1`。

### 密钥层次与轮换

```text
主密码 → KDF → master_key（离线，永不上传）
             → HKDF → vault_key（一个库）
                    → HKDF → item_key（一条记录）
                           → HKDF → backup_key / export_key（按用途域分离）
```

- **改主密码只重新派生 `master_key`**，条目密钥由 HKDF 重新导出，无需重加密全部条目——这是分层
  设计的最大收益；必须全量重加密的场景只有 `master_key` 本身泄露。轮换做成可中断任务：旧钥解密 →
  新钥加密 → 原子写回 → 记录进度，失败可续跑。
- 密钥**禁止入库、禁止进 Git、禁止进前端产物**；服务端由环境变量或密钥管理服务注入（见 `05-server-ops.md`）。

### 本地加密数据库与主密码解锁

- 落地形态二选一：① 应用层加密（条目密文存普通 SQLite，元数据列可查）；② 库级加密（SQLCipher 一类，
  `待核实`：其开源版许可，商业分发前必须确认）。推荐 ①：密钥层次可控、可做字段级 AAD、便于同步。
- 解锁流程：输入主密码 → 本地 KDF（200–500 ms）→ 校验 `auth_hash` → 派生并只把 `master_key`
  留在内存 + 少量 `item_key` 缓存 → 进入已解锁态。
- 失败处理：连续 5 次失败后延迟按 5s / 30s / 5min 递增，本地重试上限（如 10 次）；
  "失败后清空本地库"必须由用户显式确认。内存中持久明文用 `bytearray` 并在用后主动清零；
  **Python 的 `str`/`bytes` 不可变、无法可靠清零**，只能减少副本、缩短生命周期、绝不放进日志与崩溃上报。

### 多设备同步与冲突

- 同步的是密文，服务端只存储与定序，看不到内容也不做合并。
- 每条记录带 `item_uuid`、`device_id`、`rev`（单调递增）、`updated_at`、`deleted` 墓碑。
- 冲突按字段或条目二选一：LWW（简单，会丢一侧修改，适合单值字段）或保留双版本让用户选择
  （安全类产品更常见）。**禁止静默丢弃一侧修改**。
- 设备本地时间不可信：定序用服务端序号或向量时钟，本地时间只用于展示。
- 删除必须留墓碑，否则离线设备会"复活"已删条目；墓碑保留期给具体天数（如 30 天）并说明依据。
- 同步写接口必须幂等（`request_id` + 唯一索引，见 `09-production-engineering.md`），重试不得产生重复条目。
### 备份与恢复

- 备份文件本身就是攻击目标：用独立的 `backup_key` 重新加密（不是直接拷库文件），
  **禁止出现明文备份**；文件头写明版本与 KDF 参数，保证多年后仍可解密。
- 保留"导出为明文"的显式危险操作 + 二次确认，因为用户确实需要迁移。
- **恢复没演练过就等于没有备份**：把"在干净设备上从备份恢复到可读状态"列入发布前检查项，每季度演练并记录耗时；若"备份能解开但条目密钥派生失败"，通常是 `info` 或版本头被改动。
### 内存安全、剪贴板与自动锁定

- 剪贴板：复制密码后 **30 秒自动清空**（可配置 15–60 秒）；清空前校验剪贴板内容仍是自己写入的值，
  避免误删用户后来复制的内容；提示用户关闭系统剪贴板历史与跨设备同步。
- 自动锁定：空闲 **5 分钟**（可配置 1/5/15 分钟），并在切到后台、屏幕锁定、休眠唤醒、
  系统时间大幅跳变时**立即锁定**。锁定 = 清零内存密钥 + 关闭解密缓存，不只是盖住界面。
- `待核实`：各平台防截屏 / 安全窗口标记 API 的可用性与限制，需按平台官方文档确认。

### 审计与防篡改

- 记录：解锁成功/失败、条目增删改、新增设备、导出、备份、恢复、密钥轮换、越权拒绝。
- 防篡改：审计条目做**哈希链**（`hash_n = H(hash_{n-1} || entry_n)`）或对批次 HMAC 签名，可检测
  删除与插入；仅有哈希链时攻击者可整链重算，因此**定期把链头哈希写入用户可见位置或服务端只写日志**。

### 服务端侧：传输、CORS、限流、越权、日志脱敏

- **传输安全**：全站 HTTPS，TLS 1.2 起（推荐 1.3），HSTS `max-age=31536000; includeSubDomains`；
  详见 `05-server-ops.md`。`待核实`：是否为移动端引入证书固定（pinning）。
- **CORS**：显式来源白名单，绝不 `Allow-Origin: *` 搭配 `Allow-Credentials: true`；
  `Access-Control-Max-Age: 600`。
- **限流**：登录/注册按"账号 + IP"双维度，起点 **账号 5 次/15 分钟、IP 20 次/15 分钟**，超限 429；
  同步接口按用户维度（如 60 次/分钟，按客户端批量大小调整）。
- **越权（IDOR）与横向权限**：每个"按 ID 取资源"的接口**必须把当前用户/租户写进查询条件**，
  不允许"先按 ID 查出来再 if 判断"；RBAC 只管"角色能做什么动作"，对象级授权才管"这条数据是不是你的"，
  两者都要做。设备类业务的等价场景是"别人的设备能不能控制"（见 `03-app-web-backend.md`）。
- **日志脱敏**：口令、Token、主密钥、条目明文、完整卡号/证件号一律不落日志，只记 `user_id`、
  `device_id`、事件类型、结果、`trace_id`；在日志中间件做字段白名单，而不是靠每个调用点自觉。
- 认证失败统一返回同一形态，避免用错误码或耗时差异枚举账号。
- **零知识下的取舍**：零知识同步意味着**无法提供"忘记密码找回"**——能重置主密码的一方就拥有
  解密能力，这必须在需求阶段与用户协议里写明，不能事后补。可选折中：由用户离线保存高熵恢复码，
  仅用于重建 `master_key`；恢复码泄露等价于主密码泄露，同样按密钥级别保护。

### 安全测试项（发布前逐条验证，前 10 项为必过项）

| # | 测试项 | 通过判据 |
|---|---|---|
| 1 | 密文重排 | 把 A 条目密文写入 B 条目，解密必须失败（AAD 生效） |
| 2 | nonce 唯一性 | 同一记录连续加密 1000 次无重复；复查无固定 nonce 或计数器拼接 bug |
| 3 | 篡改检测 | 翻转密文任一字节、截断 tag，解密全部失败且不留半截明文 |
| 4 | 口令枚举 | 连续失败触发退避与限流；响应时间与错误信息不泄露账号是否存在 |
| 5 | 越权访问 | 用 A 的 Token 读写 B 的条目与设备，全部 403/404 |
| 6 | 重放攻击 | 重放已同步的写请求，幂等生效、不产生重复条目 |
| 7 | 备份恢复 | 干净设备 + 仅备份文件，完整恢复到可读状态（记录耗时） |
| 8 | 日志泄露 | 抓取全部日志与崩溃上报，检索不到口令、Token、明文条目 |
| 9 | 版本回滚 | 改回旧版本头或用旧客户端写入，不得静默降级或写坏数据 |
| 10 | 自动锁定 | 空闲超时、切后台、休眠唤醒后内存密钥确实被清零（调试器验证） |
| 11 | 剪贴板 | 复制密码 30 秒后清空；此间用户复制的其他内容不被误删 |
| 12 | 冲突处理 | 两端离线各改同一条目再同步，无一侧修改被静默丢弃 |
| 13 | 依赖漏洞 | CI 依赖扫描无高危项（见 `10-enterprise-process.md`） |

## 常见坑与验收标准

**高频坑**

- 用 bcrypt 或 SHA-256 派生加密密钥；验证链与加密链共用 salt 或共用一份派生输出——
  验证哈希一旦泄露，加密密钥的搜索空间随之缩小。
- 同一密钥下 nonce 重复（固定 nonce、拿条目名当 nonce、计数器重启后归零）。
- 用自创"加密后再统一 HMAC"替代 AEAD，且忘记把元数据纳入认证范围。
- 解密失败走"容错"分支，把攻击转化为静默数据损坏。
- 先 `WHERE id = ?` 再在业务层判断归属，漏一处即越权。
- 把"服务端登录成功"当成"本地 `master_key` 派生正确"。
- 备份明文，或备份直接用主密钥加密而无独立 `backup_key`，导致换密码后旧备份作废。
- 明文驻留内存期间崩溃上报把口令一并带走；`待核实`：平台 Keychain / Keystore 的访问控制参数与
  生物识别绑定细节、第三方库某版本的默认 KDF——必须读官方文档或源码，不得假设。

**学习写法 vs 企业写法**

- ① 初学者常写：`hashlib.sha256(password)` 存库、`AES.MODE_ECB`、密钥写死在 `config.py`、解密失败 `return None`；不涉及参数标定与数据格式设计，最快能跑起来。
- ② 企业写法：Argon2id（参数与密文同存、可升级）+ AES-256-GCM + AAD + 版本化密文头 + 密钥由环境变量或密钥管理服务注入 + 解密失败计入审计并拒绝服务 + 覆盖上表 14 项测试。
- ③ 差异原因：密码学是**不可检测的静默失效**——ECB 与重复 nonce 在功能测试里完全正常，只有被攻击时才表现为数据泄露；企业做法把"可升级、可验证、可审计"当硬要求，用成本换取"失效能被发现、密钥能轮换、事故能复盘"。

**验收标准（我真的会了）**

1. 能对具体功能（如"设备共享""条目同步"）写出资产 / 对手 / 攻击面 / 信任边界四栏表。
2. 能在最弱目标设备上把 Argon2id 参数标定到 200–500 ms，并说明为什么取这个值。
3. 能不看资料写出"主密码 → KDF → 主密钥 → 条目密钥"派生链，并说清哪些值可上传、哪些绝不能。
4. 能解释为什么改主密码不必重加密全部条目，以及什么情况必须重加密。
5. 能独立完成一次"干净设备 + 备份文件"恢复演练并记录耗时。
6. 上表 14 项测试能独立执行并给出证据（日志、截图、测试用例），前 10 项全过。
7. 能指出自己代码里所有明文驻留位置与清零策略，并对"按 ID 取资源"的接口做横向越权自测、改成查询条件内绑定用户。
