# 项目上下文（模板）

> **用途**：这份文件让技能知道你在做什么、卡在哪，从而给出针对性的指导，而不是泛泛而谈。
> **隐私提醒**：它通常包含你的项目细节。如果本技能目录是公开仓库，请把填写后的版本另存到你的
> 本地档案目录（见 `SKILL.md` 的"学习档案"一节），**不要提交到公开仓库**；仓库里的模板保持原样即可。
> 删除本行以上的说明、保留下面的结构也可以。

## 使用方式

1. 复制本文件到你的本地档案目录，命名如 `projects.md`。
2. 每个项目填一张卡（至少填第一个）。
3. 把"待核实清单"当成规则：**没核实前不得当作事实**，无论是对你自己还是对 AI。
4. 项目变了就更新它——它过时会导致错误的建议。

```markdown
- 明显缺口：<知道有问题但还没处理的地方：测试、监控、文档、迁移……>
- 待核实清单：<见下表>
```

## 待核实清单

> 规则：任何"我以为是这样"的技术事实都先放这里，核实后再转成结论并写进项目卡。
> 典型需要核实项：第三方 SDK 的接口名与调用约定、协议帧格式、消息主题命名、端口与地址、
> 云服务配额与计费、库的版本行为差异、部署环境的实际版本。

| 条目 | 为什么重要 | 如何核实（文件/命令/文档） | 状态 |
| --- | --- | --- | --- |
| 例：设备 SDK 的连接与停止接口 | 决定控制层适配怎么写 | 读 SDK 头文件/示例代码 | 待核实 |
|  |  |  |  |

## 填写示例（帮助你理解颗粒度）

```markdown
## 项目：<示例>内部工单系统
- 一句话定位：给 30 人的客服团队记录与流转工单
- 当前阶段：内测
- 我的角色：独立开发
- 技术栈：FastAPI + PostgreSQL + Redis + Docker Compose（部署在一台 2C4G 云主机）
- 业务域：账号与角色、工单流转、附件、通知、统计报表
- 数据规模：日增约 500 张工单，峰值约 20 QPS
- 最难的技术点：状态流转的并发冲突（两人同时接单）
- 约束：预算每月 100 元以内；只有我一个人维护
- 已完成：核心 CRUD、登录、附件上传
- 明显缺口：无自动化测试、无监控告警、数据库无迁移脚本、密钥写在 .env 明文
- 待核实清单：云主机是否支持自动快照、当前 PostgreSQL 小版本
```

颗粒度就是这个水平：**具体到能被验证**，不要写"我要做一个很厉害的系统"。
