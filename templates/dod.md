# 功能交付检查单（Definition of Done）

> 用法：一个功能**开始前**先扫一遍知道要交什么；**交付前**逐条勾选。
> 带 ★ 的是必选项，缺一项就不算交付完成（不是"下次补"）。

## 一、需求与设计

- [ ] ★ 需求能用一句话说清：谁、在什么场景、要解决什么问题
- [ ] ★ 业务流程画出来了（含异常分支，不只是顺利路径）
- [ ] ★ 明确列出本次**不做**什么（防止范围蔓延）
- [ ] 关键取舍写进了 ADR（`templates/adr.md`）

## 二、接口与数据

- [ ] ★ 接口契约明确：路径、方法、请求体、响应体、状态码、错误码
- [ ] ★ 数据库变更通过迁移脚本（Alembic），可正向也可回滚
- [ ] ★ 新增查询有对应索引，并说明服务哪个查询
- [ ] 分页/排序/过滤参数有默认值与上限（防止一次拉全表）
- [ ] 敏感字段不入库明文、不出现在日志

## 三、代码质量

- [ ] ★ 分层正确：路由不写业务、业务不直连 SQL 细节、外部依赖走 Adapter
- [ ] ★ 类型标注完整，函数职责单一
- [ ] ★ 统一异常处理生效（未捕获异常返回规范 JSON，生产不泄漏堆栈）
- [ ] 命名一致、无重复代码、无注释掉的死代码
- [ ] 配置来自环境变量，密钥不硬编码

## 四、可靠性与边界

- [ ] ★ 外部调用设了超时（连接/读取），不会无限等待
- [ ] ★ 需要重试的地方用了指数退避 + 上限（通常 3 次）
- [ ] ★ 写操作幂等（request_id / 唯一索引 / Redis 标记）
- [ ] 并发场景验证过（重复提交、并发改同一条记录）
- [ ] 依赖不可用时有明确行为：快速失败或降级，而不是挂起

## 五、测试

- [ ] ★ 单元测试覆盖核心逻辑与边界（空值、越界、权限不足）
- [ ] ★ 接口测试至少覆盖：成功、参数错误、未认证、无权限
- [ ] 集成测试跑通了真实数据库/Redis（不是全 Mock）
- [ ] 手工验证过异常路径（拔网线/停服务/传脏数据）

## 六、可观测性

- [ ] ★ 结构化日志，关键路径带 trace_id/request_id
- [ ] ★ 健康检查覆盖依赖（数据库、Redis、MQTT 等）
- [ ] 关键指标有采集（QPS、错误率、延迟、队列积压）
- [ ] 有告警规则或至少知道"出了问题看哪里"

## 七、安全

- [ ] ★ 权限校验不只查登录，还查资源归属（防越权/IDOR）
- [ ] ★ 输入有校验（类型、长度、范围、白名单）
- [ ] 敏感信息脱敏（日志、错误响应、监控标签）
- [ ] 依赖无已知高危漏洞

## 八、文档与交付

- [ ] ★ README 或接口文档更新（别人能照着跑起来）
- [ ] ★ 部署/配置变更写清（新环境变量、新服务、新端口）
- [ ] 变更说明与影响范围（谁需要配合改）
- [ ] 回滚方案明确（命令或步骤，含预计耗时）

## 九、上线

- [ ] ★ 先在测试环境验证，再到生产
- [ ] ★ 数据迁移在备份之后执行，且演练过恢复
- [ ] 灰度或分批发布（可快速回滚）
- [ ] 上线后观察窗口（至少 30 分钟看错误率与延迟）

## 十、复盘

- [ ] 记录本次实际耗时与预估差异
- [ ] 记录踩到的坑与下次规避方式
- [ ] 需要固化的检查项追加到本检查单
